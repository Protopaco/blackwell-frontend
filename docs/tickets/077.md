# [077] BUG - Non-numeric cell values silently corrupt timesheet reads instead of erroring

**Board status:** Backlog
**Reported:** 2026-08-12

## Background

**This is `blackwell-backend` work.**

Found while designing the clock-in/clock-out timesheet mode ([relates to the new read-path validation
being added there]). The existing hours-based read path has no validation on numeric cell parsing:

- `readTimesheetEntries.ts` — `Number(cellValue)` on each hours cell, guarded only against `undefined`/
  `''`. A stray non-numeric character produces `NaN`, which is not caught by `if (hours === 0) continue`,
  so it's pushed into the entries array and silently poisons the employee's total downstream (`NaN`
  propagates through the `+=` in `buildSummaryRows.ts`) — no error, no log, a corrupted payroll report.
- `readTimesheetDetailFromSheets.ts` — same unvalidated `Number(...)` pattern on `totalHours` and
  `flatRateQuantity`, parsed from the "Total Hours Worked" summary cell.

There is no `isNaN`/`Number.isNaN` check, no schema validation (no Zod/Joi anywhere in the codebase), and
no existing convention for this class of error. The codebase's current posture is "trust the sheet data."

## Scope

Not fleshed out yet. At minimum:
- Add validation on parsed numeric cell values in `readTimesheetEntries.ts` and
  `readTimesheetDetailFromSheets.ts`, throwing `UnprocessableError` (matching the existing error
  convention) instead of silently propagating `NaN`.
- Decide on message content — likely employee name + date + which cell/field, for a useful error.
- Consider whether the new clock-in/clock-out read path's validation (once built) should share a common
  helper with this fix, rather than duplicating parse-and-throw logic.
