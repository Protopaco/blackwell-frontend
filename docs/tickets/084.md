# [084] Backend — grouped/reordered activities on generated timesheets

**Board status:** Backlog
**Reported:** 2026-08-17

## Background

Real client timesheets (see the "2025 Haynes, Morgan Timesheet" reference spreadsheet) organize activities
into labeled groups (e.g. "VT Grows" as a bold header, with "Relocation Hours"/"Outreach Hours" activities
under it) in a specific, deliberate order — not the current flat alphabetical list. To make generated
timesheets an actual replacement for what clients already use, activities need optional one-level grouping
plus explicit manual ordering.

**Resolved design (2026-08-17):**

- `Activity` gains two new fields: `groupLabel: string | null` and `sortOrder: number`.
- One level of grouping only — no nested subgroups. (The reference spreadsheet's "Relocation Hours"/
  "Outreach Hours" sub-nesting under "VT Grows" is out of scope; flatten to one header level.)
- Ordering across the full combined list (see below):
  1. Ungrouped activities (`groupLabel === null`) first, sorted by their own `sortOrder`.
  2. Then named groups, in **alphabetical order by `groupLabel`** (no group-level `sortOrder` for now —
     revisit if a client needs non-alphabetical group placement later).
  3. Within a group, activities sorted by their own `sortOrder`.
- An activity with no `groupLabel` renders with no header row, same as every activity today.
- A group's header row reuses the existing `buildSectionLabelRow` row builder (already used for the former
  "Hourly"/"Flat Rate" section labels) — same visual treatment, just with the group's `groupLabel` as the text.

**Revised design (2026-08-17, later same day) — TotalHours mode's Hourly/Flat Rate split removed:**

Grouping originally applied *within* each of `sortActivities.ts`'s existing buckets (`workActivities`/
`timeOffActivities` combined into an "Hourly" section, `flatRateActivities` as its own "Flat Rate" section)
— but that means a group spanning both pay types (e.g. "VT Grows" with 3 hourly activities and 1 flat-rate
activity) would render as two disconnected header rows with the same label, in two different sections. Since
an activity's pay type (`Hourly`/`Salary`/`FlatRate`) is a per-employee bridge-row concern
(`EmployeeActivityRateInput.payRateType`), not a fixed property of `Activity`, there's no way to keep a
group visually unified while still splitting by pay type.

Resolution, for **TotalHours-mode timesheets only** (`buildWeek.ts` — ClockInOut mode, `buildClockInOutTimesheet.ts`,
is unchanged and revisited later if needed):
- No more separate Hourly/Flat Rate/Time Off sections. `buildWeek.ts` combines every activity the employee
  has (work + time off + flat-rate) into **one** grouped/ordered block, using the same ordering rules above
  applied across the full combined list (re-run via `sortActivities.groupActivities`, exported for this
  purpose).
- Each activity row is tagged with a `rowType` (`Hourly`/`Salary`/`FlatRate`/`ETO`/`PTO`/`STO`, see
  `TimesheetManifest.ActivityRowType`), derived from `payRateTypeByActivityId` (now also returned by
  `sortActivities`) and `activity.payrollCategory`. The row's label cell is tinted per `rowType`
  (`formatActivityRows.ts` — a background-color tag on the existing cell, not a new column; may revisit as
  a dedicated column later if the color-only treatment isn't clear enough).
- Both Daily Total rows (Hourly and Flat Rate) are removed entirely — they were purely a display
  convenience (payroll reading has always looked up `payrollCategory`/`payRateType` per-activity, never by
  section), and summing hours/shifts/time-off together no longer means anything now that rows interleave by
  group instead of sitting in contiguous type-based blocks.
- Time off (PTO/ETO/STO) is no longer a separate visual section either — it's just part of the same combined
  list, distinguished only by its row tag, and can participate in the same free-form `groupLabel` grouping as
  everything else (a client can group PTO/ETO/STO activities under a named header if they want one, the same
  way they'd group any other activity).
- The bottom-of-sheet pay-period summary section (Total Hours Worked, Holiday Hours, PTO/ETO/STO, Flat Rate
  Shifts) is unaffected in purpose — it now reads one combined `activityRows` array per week, filtered by
  `rowType`, instead of two separate manifest arrays.
- `groupLabel` has no separate managed entity/CRUD — it's a free-form string, duplicated per activity, the
  same way `payrollCategory` and (formerly) `trackSeparately` are. The frontend ticket ([085]) handles
  surfacing existing values as autocomplete suggestions; this is purely a frontend UX concern, not a backend
  one — the API just accepts/returns whatever string it's given.
- `sortOrder` is assigned by the frontend (it already has the full activity list to compute "next position in
  this group" or a post-drag-and-drop reorder), not auto-assigned by the backend.
- **New batch-update endpoint, added 2026-08-17**: a "Save All" reorder in [085] can change `sortOrder`/
  `groupLabel` on many activities at once. The existing single-activity `PUT` does a full
  `readPayrollConfig` + `writeActivities` round-trip to the same Google Sheets workbook on every call —
  firing that once per changed activity for a bulk reorder means N redundant reads/writes against the same
  file, and risks a later call clobbering an earlier one's write if they overlap. Instead, add
  `PUT /api/v1/activity/{clientId}/batch` (same shape as `PUT
  /api/v1/payrollReport/{clientId}/{payPeriodId}/employeeExpenses/batch` from [082]): accepts an array of
  `{activityId, groupLabel, sortOrder}`, reads the config once, overlays all changes, and writes once via
  the existing `writeActivitiesBulk.ts` (already used internally by pay-period snapshot creation, just not
  exposed as an endpoint yet).

## Implementation plan

Broken into 5 sequential chunks — stop after each for review before starting the next.

1. **Model/schema/db plumbing** — add `groupLabel`/`sortOrder` to `Activity`, swagger schema,
   `ACTIVITIES_HEADERS`, db read/write mapping, devTestData seed. No sort/generation behavior change yet —
   fields just persist and round-trip. Update tests that construct `Activity` fixtures.
2. **Sort/group logic** — rework `sortActivities.ts` for the new within-bucket ordering (ungrouped-first-
   by-sortOrder, then groups-alphabetical-with-members-by-sortOrder). New unit tests covering: no groups
   (existing alphabetical behavior preserved for backward compat when all `groupLabel` are null), single
   group, multiple groups, ungrouped mixed with grouped.
3. **Generation + manifest + formatting** — for TotalHours mode, collapse the Hourly/Flat Rate/Time Off
   split into one combined grouped block in `buildWeek.ts` (delete `buildFlatRateSection.ts`), tag each row
   with `rowType`, remove the Daily Total rows, extend `TimesheetManifest`, style group headers and
   per-rowType label-cell tints. ClockInOut mode (`buildClockInOutTimesheet.ts`) left as-is aside from a
   type-compatibility fix. Update/add unit tests for row emission and manifest shape.
4. **Batch reorder endpoint** — new `ActivityReorderUpdate` model/schema, `updateActivitiesBatch.ts`
   service, `PUT /api/v1/activity/{clientId}/batch` route, unit tests.
5. **Integration tests + OpenAPI regen** — update integration tests (including the new batch endpoint), run
   `npm run generate`.
