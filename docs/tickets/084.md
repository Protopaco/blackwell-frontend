# [084] Backend — grouped/reordered activities on generated timesheets

**Board status:** Backlog
**Reported:** 2026-08-17

## Background

Real client timesheets (see the "2025 Haynes, Morgan Timesheet" reference spreadsheet) organize activities
into labeled groups (e.g. "VT Grows" as a bold header, with "Relocation Hours"/"Outreach Hours" activities
under it) in a specific, deliberate order — not the current flat alphabetical list. To make generated
timesheets an actual replacement for what clients already use, activities need optional one-level grouping
plus explicit manual ordering.

**Resolved design (2026-08-17):**

- `Activity` gains two new fields: `groupLabel: string | null` and `sortOrder: number`.
- One level of grouping only — no nested subgroups. (The reference spreadsheet's "Relocation Hours"/
  "Outreach Hours" sub-nesting under "VT Grows" is out of scope; flatten to one header level.)
- Grouping applies **within** each existing bucket (`workActivities`/`timeOffActivities` combined into the
  Hourly section, and `flatRateActivities`) — a group cannot span across those buckets. This keeps
  `sortActivities.ts`'s existing work/time-off/flat-rate split untouched; grouping is a finer sort applied
  inside each bucket.
- Ordering within a bucket:
  1. Ungrouped activities (`groupLabel === null`) first, sorted by their own `sortOrder`.
  2. Then named groups, in **alphabetical order by `groupLabel`** (no group-level `sortOrder` for now —
     revisit if a client needs non-alphabetical group placement later).
  3. Within a group, activities sorted by their own `sortOrder`.
- An activity with no `groupLabel` renders with no header row, same as every activity today.
- A group's header row reuses the existing `buildSectionLabelRow` row builder (already used for "Hourly"/
  "Flat Rate" section labels) — same visual treatment, just with the group's `groupLabel` as the text.
- `groupLabel` has no separate managed entity/CRUD — it's a free-form string, duplicated per activity, the
  same way `payrollCategory` and (formerly) `trackSeparately` are. The frontend ticket ([085]) handles
  surfacing existing values as autocomplete suggestions; this is purely a frontend UX concern, not a backend
  one — the API just accepts/returns whatever string it's given.
- `sortOrder` is assigned by the frontend (it already has the full activity list to compute "next position in
  this group" or a post-drag-and-drop reorder), not auto-assigned by the backend.
- **New batch-update endpoint, added 2026-08-17**: a "Save All" reorder in [085] can change `sortOrder`/
  `groupLabel` on many activities at once. The existing single-activity `PUT` does a full
  `readPayrollConfig` + `writeActivities` round-trip to the same Google Sheets workbook on every call —
  firing that once per changed activity for a bulk reorder means N redundant reads/writes against the same
  file, and risks a later call clobbering an earlier one's write if they overlap. Instead, add
  `PUT /api/v1/activity/{clientId}/batch` (same shape as `PUT
  /api/v1/payrollReport/{clientId}/{payPeriodId}/employeeExpenses/batch` from [082]): accepts an array of
  `{activityId, groupLabel, sortOrder}`, reads the config once, overlays all changes, and writes once via
  the existing `writeActivitiesBulk.ts` (already used internally by pay-period snapshot creation, just not
  exposed as an endpoint yet).

## Full touchpoint inventory

**Model / schema / config**
- `src/models/Activity.ts` — add `groupLabel: string | null`, `sortOrder: number`
- `src/utils/swagger/schema/activity.ts` — OpenAPI schema properties
- `src/config/constants.ts` — `ACTIVITIES_HEADERS` (new sheet columns; decide column position — likely
  appended at the end to avoid reflowing existing columns)

**DB layer**
- `src/db/activity/mapActivity.ts` — read mapping (sheet row → `Activity`)
- `src/db/activity/mapActivityRow.ts` — write mapping (`Activity` → sheet row)
- `src/db/activity/appendActivity.ts` — append-row payload

**Sort/group logic**
- `src/services/timesheet/sortActivities.ts` — rework the alphabetical sort within each bucket
  (`workActivities`, `timeOffActivities`, `flatRateActivities`) into: ungrouped-by-sortOrder, then
  groups-alphabetical-by-groupLabel with members-by-sortOrder. Consider whether `SortedActivities`' shape
  needs to expose group boundaries explicitly (e.g. an ordered list of `{ groupLabel: string | null,
  activities: Activity[] }` per bucket) so `buildWeek.ts`/`buildClockInOutTimesheet.ts` don't need to
  re-derive grouping themselves.

**Generation**
- `src/services/timesheet/buildWeek.ts` — emit a `buildSectionLabelRow(groupLabel, maxDays)` row before
  each group's activity rows within the Hourly section (currently just emits one "Hourly" label then all
  activities flat — see lines ~60-74)
- `src/services/timesheet/buildFlatRateSection.ts` — same, for the Flat Rate section
- `src/services/timesheet/buildClockInOutTimesheet.ts` — same treatment for the ClockInOut layout's Hourly
  and per-day Flat Rate sections
- `src/models/TimesheetManifest.ts` — extend `WeekManifest`/`ClockInOutWeekManifest` (or
  `ActivityRowManifest`) to track group-header row numbers, the same way `hourlySectionLabelRow` is
  tracked today — needed so formatting can style them and so reading logic can keep skipping them (group
  header rows are not tied to any activity, same as today's section-label rows)
- `src/services/timesheet/formatWeekSection.ts` / ClockInOut formatting equivalent — apply the same visual
  treatment already used for "Hourly"/"Flat Rate" section labels to group-header rows

**Batch reorder endpoint**
- `src/models/ActivityReorderUpdate.ts` (new) — `{ activityId: string; groupLabel: string | null;
  sortOrder: number }`
- `src/utils/swagger/schema/activityReorderUpdate.ts` (new) — OpenAPI schema def
- `src/db/activity/writeActivitiesBulk.ts` — no change needed, already writes a full activity list in one
  call; just gets a new caller
- `src/services/activity/updateActivitiesBatch.ts` (new) — reads config once, overlays `groupLabel`/
  `sortOrder` onto matching activities by `activityId`, rejects the whole batch (no partial writes) if any
  `activityId` doesn't match a known activity — same reject-on-unknown-id shape as
  `updateEmployeeExpensesBatch.ts`
- `src/routes/v1/activity/putActivitiesBatch.ts` (new) — `PUT /api/v1/activity/{clientId}/batch`, modeled
  directly on `putEmployeeExpensesBatch.ts`

## Implementation plan

Broken into 5 sequential chunks — stop after each for review before starting the next.

1. **Model/schema/db plumbing** — add `groupLabel`/`sortOrder` to `Activity`, swagger schema,
   `ACTIVITIES_HEADERS`, db read/write mapping, devTestData seed. No sort/generation behavior change yet —
   fields just persist and round-trip. Update tests that construct `Activity` fixtures.
2. **Sort/group logic** — rework `sortActivities.ts` for the new within-bucket ordering (ungrouped-first-
   by-sortOrder, then groups-alphabetical-with-members-by-sortOrder). New unit tests covering: no groups
   (existing alphabetical behavior preserved for backward compat when all `groupLabel` are null), single
   group, multiple groups, ungrouped mixed with grouped.
3. **Generation + manifest + formatting** — wire group-header rows into `buildWeek.ts`,
   `buildFlatRateSection.ts`, `buildClockInOutTimesheet.ts`; extend `TimesheetManifest`; style the new rows.
   Update/add unit tests for row emission and manifest shape.
4. **Batch reorder endpoint** — new `ActivityReorderUpdate` model/schema, `updateActivitiesBatch.ts`
   service, `PUT /api/v1/activity/{clientId}/batch` route, unit tests.
5. **Integration tests + OpenAPI regen** — update integration tests (including the new batch endpoint), run
   `npm run generate`.
