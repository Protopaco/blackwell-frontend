# [063] Employee Activity Rates in Employee Dialog (Epic)

**Board status:** Ready (epic — tracked as a group, broken into tickets 064-065)
**Depends on:** [049], [051] (blackwell-backend — EmployeeActivityRates embedded in Employee endpoints)

## Background

Backend epic [048] replaces per-employee hourly/holiday pay rates and per-activity flat rates with a bridge (`EmployeeActivityRates`) — one row per employee-activity pair, embedded directly in the Employee `GET`/`POST`/`PUT` payloads rather than a standalone CRUD surface (see [049]/[051]).

Resolved via design discussion:

- **Where it lives**: inside the Create/Edit Employee dialog, not a separate page or a nested dialog — logically an employee's activity assignments belong with the rest of their config.
- **Pattern to follow**: `FundingAllocationFields` on the Activity dialog is the existing precedent for "repeatable row list of sub-items edited inline within a parent entity's dialog, staged and submitted atomically" — reuse that shape rather than inventing something new.
- **Save model**: fully staged, matching `FundingAllocationFields` — rows are added/edited/removed only in local dialog state, and the whole `activityRates` array submits once when the dialog's Save button is clicked (not immediate-per-action; that alternative was considered and rejected — see epic discussion for the tradeoffs).
- **`payRate` field**: disabled (not hidden) when a row's `payRateType` is `salary`, since salary rows don't carry their own rate.
- **`salaryAmount`**: lives on Employee, not per-row. Shown behind a "Salaried" toggle (next to the existing "Active" toggle) — the amount field only appears when toggled on, to avoid a confusing always-visible field that's usually irrelevant.
- **Row cap**: none — capped only by the number of activities that exist for the client (unlike funding sources' hard cap of 3).
- **Activity dropdown**: only shows active activities, same filtering as the funding-source dropdown.
