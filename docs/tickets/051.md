# [051] Update Employee — remove old pay rates, add salaryAmount + embed activityRates

**Board status:** Backlog
**Part of:** [048] Expand EmployeeActivityRates (Epic)
**Depends on:** [049]

## Background

**This is `blackwell-backend` work.**

Pay rates move to the `EmployeeActivityRates` bridge ([049]). No back-compat needed — pre-launch, no existing clients.

Per epic discussion, there's no standalone CRUD for bridge rows — they're managed entirely through the Employee endpoints, matching the existing `Activity.fundingSources` pattern (a staged array on the parent entity, submitted atomically, reconciled server-side).

## Scope

- Remove `hourlyPayRate1`, `hourlyPayRate2`, `holidayPayRate` from `Employee`, `EmployeeCreateRequest`, `EMPLOYEES_HEADERS`, `mapEmployee.ts`/`mapEmployeeRow.ts`, swagger schemas
- Add `salaryAmount: number` (nullable/optional — absence or 0 means not salaried, no separate boolean; decided in epic discussion)
- Add `activityRates: EmployeeActivityRate[]` to the `Employee` response shape and to `EmployeeCreateRequest`/update request
- `getEmployees.ts` (and any other employee read path) joins each employee's bridge rows from [049]'s db layer by `employeeId` and embeds them
- `createEmployee.ts` — after creating the employee, appends its initial `activityRates` rows to the bridge tab
- `updateEmployee.ts` — reconciles the incoming `activityRates` array against the employee's existing bridge rows: append rows that are new, update rows that changed, delete rows that were removed from the array. Validate each row (activity exists and is active, no duplicate `activityId` within the array) before writing.
- Update employee CRUD route docs/swagger referencing the removed/added fields

## Note for later

Editing a bridge row through this path is always allowed (master PayrollConfig data is never locked — see [054] for why pay-period-scoped locking is a separate, later concern and doesn't apply here).
