# [049] EmployeeActivityRates tab infra

**Board status:** Backlog
**Part of:** [048] Expand EmployeeActivityRates (Epic)

## Background

**This is `blackwell-backend` work.**

New `EmployeeActivityRates` tab in each client's PayrollConfig workbook, one row per `(employeeId, activityId)` pair. See [048] for the full bridge design and decided row shape.

## Scope

- New `EmployeeActivityRate` model: `id, employeeId, employeeName, activityId, activityName, payRateType (hourly/flatrate/salary), payRate, holidayPayRate`
- New `payRateType` enum (`hourly`/`flatrate`/`salary`) — replaces the existing `PayRate` enum's `Hourly1`/`Hourly2`/`FlatRate1`/`FlatRate2` values, since one bridge row per pair removes the need for two hourly/flat-rate slots (confirmed in epic discussion)
- db layer following the existing per-entity convention (`mapEmployeeActivityRate.ts`, `mapEmployeeActivityRateRow.ts`, `appendEmployeeActivityRate.ts`, `writeEmployeeActivityRatesBulk.ts`, `readEmployeeActivityRates.ts`)
- `EMPLOYEE_ACTIVITY_RATES_TAB`/`_HEADERS` constants in `config/constants.ts`
- Add the new tab to `PAYROLL_CONFIG_TABS` in `src/services/client/createClient.ts` so it's provisioned for every new client
- Add the tab to `readPayrollConfig.ts`'s batched read (same pattern as the other 7 PayrollConfig tabs)
- Swagger/OpenAPI schema for the new model

## Design decision: no standalone CRUD routes

There is no dedicated `POST`/`PUT`/`DELETE /api/v1/employeeActivityRate` surface — bridge rows are managed entirely through the Employee endpoints instead (see [051]):

- `GET` employee(s) embeds `activityRates: EmployeeActivityRate[]` for each employee (backend joins by `employeeId` when building the response)
- `POST`/`PUT /api/v1/employee` accept the employee's full `activityRates` array; the service reconciles it against existing bridge rows (append new, update changed, delete removed) in one call — matches the existing `Activity.fundingSources` pattern (staged array, submitted atomically with the parent entity), rather than introducing per-row CRUD calls the frontend would need to orchestrate separately.

This tab infra ticket only needs the raw db layer (used internally by [051]'s reconciliation logic) — no routes of its own.
