# [083] Remove `Activity.trackSeparately` — no discoverable purpose

**Board status:** Backlog
**Reported:** 2026-08-17

## Background

This spans both `blackwell-backend` and `blackwell-frontend`.

`Activity.trackSeparately` (boolean, sheet column `TrackSeparately`) is stored, round-tripped through
the `Activities` tab, editable as a switch in the Activity create/edit dialog, and displayed as Yes/No
in both Activities tables. It's also treated as a "structural" field — locked once a pay period's first
timesheet is generated, alongside `activityName` and `payrollCategory` (see
`updateActivityOnPayPeriod.ts`).

Despite that, an exhaustive search of both repos found **no logic anywhere that branches on its
value** — not in timesheet generation, row builders, the Payroll Report, or the Allocation Report. It's
pure storage/display.

The user's recollection is that it was originally meant to control how an activity's hours were
presented on the Payroll Report — something like giving PTO/ETO/STO their own separate line, as opposed
to being lumped in with Regular hours. That behavior does exist today (`buildSummaryRows.ts` groups
summary rows by `employeeId + payrollCategory + payRateType + isHoliday`, so PTO/ETO/STO already get
their own rows), but it's driven entirely by `Activity.payrollCategory`, not `trackSeparately`. Best
guess: `trackSeparately` predates `payrollCategory` (or predates payrollCategory covering this case) and
was never removed once superseded — unconfirmed, since nothing in `BUSINESS_RULES.md`,
`ARCHITECTURE.md`, `TIMESHEET_STYLE_GUIDE.md`, or either ticket archive documents its purpose.

**Resolved (2026-08-17)**: confirmed safe to remove. The user added the field themselves and confirmed
it has no remaining purpose. The project is pre-production, so there are no live client workbooks to
migrate — dropping it from `ACTIVITIES_HEADERS` and the sheet mapping is sufficient, no data migration
step needed.
