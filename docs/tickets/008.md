# [008] Settings Management

**Board status:** Backlog
**Migrated from:** old `docs/TICKETS.md` "Settings Management" epic + "Resolve settings edit logic" note

## Background

Settings (`GET`/`PUT /api/v1/settings/{clientId}`) are already seeded during Client creation. No management UI exists yet — was parked 2026-07-16 pending a business-rule decision; unparked 2026-08-11 with that decision made (see below).

## Resolved business rules

- `timeInputMethod` and `payPeriodInterval` — always editable. Confirmed these are future-only edits: changing them doesn't affect any pay period already created, only how the *next* one is computed/displayed.
- `payPeriodStartDate` — only read by `getNextPayPeriod` when a client has **zero** pay periods
  (`src/services/payPeriod/getNextPayPeriod.ts:50`); once the first pay period exists, every later "next
  period" is derived from the latest existing period's `endDate`, and `payPeriodStartDate` is never read
  again. So:
  - If the client has 0 pay periods — field is editable. This also covers seasonal/irregular employers:
    a client can sit dormant indefinitely, and whenever they're ready to start payroll, `payPeriodStartDate`
    is set to whatever date makes sense at that time.
  - If the client has ≥1 pay period — field is disabled, with a tooltip explaining this value is no
    longer used.
- Explicitly out of scope for now: any notion of "skipping" or making pay periods ad-hoc beyond what the
  interval already allows. Can be revisited later if a real need comes up.

## Scope

Not fully fleshed out yet — needs a design pass for where this UI lives (likely alongside
`ClientInfoManagement` from [062], possibly its own settings section) before estimating. At minimum:
- A Settings management UI exposing `timeInputMethod`, `payPeriodInterval`, `payPeriodStartDate`
- `payPeriodStartDate` disabled + tooltip when the client has ≥1 pay period (frontend gate); decide
  whether the backend `PUT /api/v1/settings/{clientId}` should also reject changes to this field once
  pay periods exist, or whether frontend-only gating is sufficient given the field is already inert
  server-side at that point
