# [081] Persist clock-in/clock-out hours into the payroll report

**Board status:** Backlog
**Reported:** 2026-08-12
**Verified:** 2026-08-13
**Depends on:** [079], [080]

## Background

**This is `blackwell-backend` work.**

Fourth piece of adding the clock-in/clock-out timesheet mode. `readTimesheetEntries` (as extended by
[079]) produces the same `TimesheetEntry` shape (`employeeId`, `activityId`, `date`, `hours`,
`isHoliday`, `payRateType`) regardless of which mode the entries came from, so `generatePayrollReport.ts`
and the downstream `buildHoursRows.ts`/`buildSummaryRows.ts` should need little to no change to consume
clock-in/clock-out-sourced entries correctly.

This ticket is to actually confirm that end-to-end — run a `ClockInOut` client's timesheets through
`generatePayrollReport` and verify the written report (hours tab + summary tab) is correct — and catch
anywhere in that path that turns out to make an assumption specific to the Hours mode (e.g. anything
that inspects `WeekManifest.activityRows` directly rather than going through the already-abstracted
`TimesheetEntry` output).

## Scope (as verified)

- End-to-end verification done via live testing against a real `ClockInOut` client, not a synthetic
  unit-level integration test: generated a `ClockInOut` timesheet ([078]), entered sample clock-in/out
  data, ran `generatePayrollReport`, confirmed the `current_hours`/`current_payroll_summary` tabs
  matched expected values.
- `generatePayrollReport.ts`, `buildHoursRows.ts`, and `buildSummaryRows.ts` were all audited and
  confirmed mode-agnostic — none of them inspect `WeekManifest.activityRows` or any other
  TotalHours-specific shape directly; they consume the already-abstracted `TimesheetEntry[]` output from
  `readTimesheetEntries.ts` identically regardless of source mode. **No changes were needed in any of
  these three files.**
- Open question from the original ticket (should the report show clock-in/out-specific data like actual
  clock times) — resolved: the report stays mode-agnostic, aggregated-hours-only. No client requirement
  surfaced for anything more.

## A real bug was found and fixed during this verification (unrelated to [079]/[080]/[078] logic)

Live testing surfaced a payroll-report generation failure for a salaried employee with legitimate hours
booked against an Hourly-configured activity that had recently been changed to Salary in the employee's
`EmployeeActivityRates` (EAR) config — `readTimesheetEntries` was returning 0 entries for that
employee even though the timesheet itself was correctly filled in.

Root cause was **not** a bug in the new ClockInOut read path (confirmed via isolated repro tests, a
temporary debug log, and careful review of the real manifest/log output) — the `readClockInOutSlotRows`
logic was reading and validating correctly given the data it received. The actual cause: a stale
`payPeriodConfigSnapshotCache` entry (24h TTL, keyed by `payrollReportFileId`), which had cached the pay
period's employee/activity config from before the employee's EAR row was updated.

**A fix was written and then reverted after deeper investigation.** The first attempt added
`payPeriodConfigSnapshotCache` invalidation to `updateEmployee.ts` (mirroring `updateSettings.ts`'s
pattern), on the theory that any client-wide employee edit should invalidate every one of the client's
pay-period snapshot caches. Auditing the surrounding architecture afterward
(`readPayPeriodConfigSnapshot.ts`, `addEmployeeToPayPeriod.ts`, `createPayPeriodConfigSnapshot.ts`)
showed this was inert: **pay periods hold a frozen, point-in-time copy of PayrollConfig, seeded once at
pay-period creation** — general client-wide CRUD (`updateEmployee`, `createActivity`, `updateActivity`,
`deleteActivity`, `createEmployee`, funding-source/holiday CRUD) never writes into an existing pay
period's embedded snapshot tabs at all, so nothing about `updateEmployee.ts` invalidating that cache
could have been the actual fix — a fresh server process (cold cache) happened to coincide with the
retest that "confirmed" it. The `updateEmployee.ts`/`updateEmployee.test.ts` changes were reverted back
to their original state; verified clean (typecheck, build, 528/528 unit tests).

**Resolved**: pay-period config snapshots being frozen at creation time is intentional, not a gap —
confirmed by the user (2026-08-13). Only the explicit `addXToPayPeriod` / `removeXFromPayPeriod` /
`updateActivityOnPayPeriod` / `syncHolidaysOnPayPeriod` family of services re-syncs an *existing* pay
period's embedded config from the live client config; general client-wide CRUD deliberately does not
propagate into pay periods that already exist. This is required for the work (each pay period is meant
to be a stable, point-in-time record), not something to fix. No further action needed here.
