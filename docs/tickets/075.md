# [075] Redundant fetch calls during timesheet generation polling

**Board status:** Backlog

## Background

**This is `blackwell-frontend` work.**

Found via the browser Network tab while generating timesheets. Every fetch is attributed to the same
generated-client wrapper (`runtime.ts:206`), so this doesn't identify the actual call site — that's
still to be found.

Two things stood out:

- `summary` and `next` (and other resources) each fire twice in immediate succession — one 200, one
  304 — before anything else happens.
- While a `generate` request is pending, the same per-employee UUID-keyed endpoint (e.g.
  `770c1a57-d806-4667-8fae-aaa8340b27a1`, `08d66507-d5f8-4114-9ec1-6c4eda2be923`) is hit repeatedly,
  each time paired with a `config` and/or `summary` re-fetch, each pair also showing a 200 then a 304.
  This looks like status polling for generation progress, but it's re-fetching `config`/`summary`
  alongside every poll tick rather than just the one status resource that actually changes.

Not yet confirmed whether this is a real bug (duplicate effect/hook firing twice, or a poll loop
over-fetching) or intentional revalidation behavior from whatever data-fetching library/pattern is in
use. Low urgency — the 304s are cheap — but worth tracking down since it's a lot of redundant network
traffic during generation.

## Scope

Not fleshed out yet — needs investigation before estimating. At minimum:
- Find the actual call site(s) behind the polling loop (start from wherever "Generate Timesheets" kicks
  off status polling)
- Determine whether `summary`/`config` genuinely need to be re-fetched on every poll tick, or only the
  per-employee status resource
- Determine whether the initial `summary`/`next` double-fetch (200 then 304) is duplicate calls or
  intentional revalidation, and fix if duplicate
